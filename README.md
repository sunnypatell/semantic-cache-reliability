> A semantic cache reuses a stored answer whenever a new prompt's embedding is close enough
> to an earlier one, trading a model call for a lookup. This project asks the question the
> literature has mostly skipped: when the closeness test is wrong, what does it cost? We
> separate *cache-equivalence* (safe to reuse the stored answer) from mere *embedding
> similarity*, measure how often embedding caches serve a wrong answer across models,
> thresholds, and domains, trace that error into downstream task quality, and derive a
> cost-aware way to set the operating point.

## What the study finds

- The property a cache needs, whether one prompt's answer is valid for another, is not the
  cosine similarity it can measure. The two come apart most where it matters: on adversarial
  near-duplicate prompts, the strongest embeddings separate equivalent from non-equivalent
  pairs barely above chance, so the cache is effectively blind to the distinction that
  decides whether reuse is safe.
- Keeping a cache honest is expensive. To hold the false-hit rate under one percent, even
  the best encoder can serve only a small share of traffic on clean domains, and almost
  nothing on the adversarial one.
- A false hit is not equally costly everywhere: it depends on where the cache sits in the
  pipeline. A cost-aware threshold tied to the measured penalty of a false hit improves the
  cost-coverage trade-off over a fixed default and over a correctness-bounding threshold,
  and it transfers across domains for a fixed encoder.

## Repository layout

```
paper/            LaTeX source (main.tex), sections/, tables/, figures/, matplotlib style
src/cacherel/     Python package: embeddings, cache-reliability metrics, calibration, BCa stats
experiments/      Runnable scripts (reliability, calibration, downstream, figures, tables, run_all)
data/             Labeled cache-equivalence pairs (processed) + provenance; raw data is gitignored
results/          Generated per-(domain, encoder) reports and summary CSVs
research/          Conventions knowledge base, decision record, preregistration
tests/            Unit tests for metrics and statistics
```

## Reproducing the results

Requirements: Python 3.12, and (for the paper) a TeX distribution with `biber`.

**Linux / macOS (bash):**

```bash
# 1. Environment
python3 -m venv .venv && source .venv/bin/activate
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install -r requirements.txt && pip install -e .

# 2. Reproduce every result, figure, and table (CPU only)
python experiments/run_all.py

# 3. Compile the paper (needs a TeX distribution with biber)
latexmk -pdf -cd paper/main.tex
```

**Windows (PowerShell):**

```powershell
# 1. Environment
python -m venv .venv ; .\.venv\Scripts\Activate.ps1
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install -r requirements.txt ; pip install -e .

# 2. Reproduce every result, figure, and table (CPU only)
python experiments\run_all.py

# 3. Compile the paper (builds locally; see build.ps1)
powershell -File build.ps1
```

A `Dockerfile` reproduces the experiments in a pinned container (`docker build -t cacherel .`
then `docker run --rm -v ${PWD}/results:/app/results cacherel`). Random seeds are fixed, so
figures and tables regenerate deterministically.
